## fr

> *Cet article est né d'une revue de sécurité de Workbench menée avec Claude, un assistant IA d'Anthropic. Les expériences et les tests cités ont été exécutés pendant cette revue.*

### Le contexte

Mediakit est une application de bureau : on l'installe, elle démarre un petit serveur FastAPI sur la machine, et l'interface s'ouvre dans le navigateur. Une seule personne est censée lui parler : celle qui est assise devant l'ordinateur.

Pourtant, en relisant le code de démarrage lors d'une revue de sécurité, une ligne m'a arrêté :

```python
host="0.0.0.0",
```

Ça fonctionnait parfaitement, et c'est bien le problème : cette ligne n'a jamais provoqué la moindre erreur. Elle a simplement rendu l'API de Mediakit, **sans aucune authentification**, accessible à tout le réseau auquel l'ordinateur était connecté.

### Une adresse d'écoute n'est pas une adresse de destination

Quand un serveur démarre, il choisit sur **quelle interface réseau** il écoute. C'est ce que fait l'argument `host`. Une machine en a plusieurs : la boucle locale (`127.0.0.1`, qui ne sort jamais de la machine), le Wi-Fi, l'Ethernet, parfois un VPN ou Docker.

* `127.0.0.1` : le serveur n'écoute que sur la boucle locale. Seule cette machine peut s'y connecter.
* `0.0.0.0` : « toutes les interfaces ». Le serveur répond sur chacune des adresses de la machine.

Je l'ai vérifié avec quelques lignes de Python. Je lie un serveur, puis j'essaie de m'y connecter par l'adresse de la boucle locale et par l'adresse réseau de la machine (`192.0.2.2` ici) :

```
serveur lié à 127.0.0.1 -> via 127.0.0.1 : connecté | via 192.0.2.2 : ConnectionRefusedError
serveur lié à 0.0.0.0   -> via 127.0.0.1 : connecté | via 192.0.2.2 : connecté
```

Même programme, même port. La seule différence est la valeur de `host`, et elle décide si un autre appareil peut frapper à la porte.

Un détail qui prête à confusion : `0.0.0.0` n'a pas le même sens côté **client**. Si vous vous *connectez* à `0.0.0.0` sous Linux, la connexion aboutit sur votre propre machine. Je l'ai testé aussi. On y reviendra, car c'est exactement ce qui a causé une faille de navigateur.

### Pourquoi 0.0.0.0 est si tentant

Parce que ça « marche partout ». Un serveur en `127.0.0.1` est invisible depuis un conteneur Docker, depuis WSL, depuis votre téléphone. Un serveur en `0.0.0.0` répond à tout le monde, et le problème disparaît. Les tutoriels le recommandent par réflexe, et beaucoup d'outils de développement le proposent en option.

Le piège, c'est qu'on règle un problème de **connectivité** en ouvrant un trou de **sécurité**, sans le voir, parce que tout continue de fonctionner.

### Ce que ça expose

Sur le Wi-Fi d'un café, d'une université ou d'un coworking, n'importe quel appareil du même réseau pouvait appeler l'API de Mediakit. Le pire dans mon cas : Mediakit propose un « mode avancé » qui permet de lancer des commandes sur des outils comme FFmpeg avec des options choisies par le client. Une API qui lance des processus, ouverte au réseau local sans mot de passe, c'est une porte ouverte.

### Même 127.0.0.1 ne suffit pas

Passer en `127.0.0.1` règle le problème du réseau. Mais il reste une porte que beaucoup oublient : **votre navigateur**.

Quand vous visitez un site quelconque, le JavaScript de cette page s'exécute *sur votre machine* et peut envoyer des requêtes à `http://127.0.0.1:PORT`. Trois attaques en découlent :

* **CSRF** : un `fetch()` en POST avec un corps `multipart/form-data` est une « requête simple » pour le navigateur, qui l'envoie **sans demander la permission** (pas de pré-vol CORS). La page ne peut pas lire la réponse, mais le serveur a exécuté l'action.
* **WebSocket cross-site** : les WebSockets ne sont soumis à aucun contrôle CORS. N'importe quelle page peut s'y connecter et lire les logs d'un job.
* **DNS rebinding** : un site malveillant fait pointer `evil.example` vers `127.0.0.1` après coup. Pour le navigateur, l'application devient alors « de la même origine » que la page.

Et `0.0.0.0` a lui-même été exploité de ce côté. En 2024, Oligo Security a publié la faille « 0.0.0.0 Day » : des sites web pouvaient atteindre des services locaux en passant par `0.0.0.0`, en contournant les protections des navigateurs contre l'accès au réseau privé. Les navigateurs ont depuis commencé à bloquer ces requêtes. Mais la leçon reste : **une application locale ne doit pas supposer que le navigateur la protège**.

### La défense : vérifier Host et Origin

Deux en-têtes suffisent à fermer ces portes. Un navigateur envoie toujours `Origin` sur les requêtes cross-origin et les WebSockets, et `Host` indique le nom utilisé pour joindre le serveur.

```python
LOOPBACK = {"127.0.0.1", "localhost", "::1"}

def refuse(headers) -> str | None:
    if hostname(headers.get("host", "")) not in LOOPBACK:
        return "Host non autorisé"            # anti DNS rebinding
    origin = headers.get("origin")
    if origin and urlsplit(origin).hostname not in LOOPBACK:
        return "Origin non autorisé"          # anti CSRF / WebSocket cross-site
```

J'en ai fait un middleware réutilisable (`LocalOnlyGuard`) pour Workbench. Vérification en conditions réelles, sur le serveur lancé :

```
POST avec  Origin: https://evil.example  ->  403 FORBIDDEN_ORIGIN
GET  avec  Host: evil.example:8768       ->  403 FORBIDDEN_ORIGIN
GET  depuis la propre interface          ->  200
```

Les clients qui ne sont pas des navigateurs (curl, scripts) n'envoient pas `Origin` et restent acceptés tant que `Host` est local. L'interface de l'application, elle, continue de fonctionner normalement.

### Le piège de Docker

Dans un conteneur, une application écoute généralement sur `0.0.0.0` : sinon Docker ne pourrait pas lui transmettre le trafic. Ce n'est pas un défaut. Ce qui décide de l'exposition, c'est la **publication du port** :

```bash
docker run -p 8000:8000 mon-image              # publié sur 0.0.0.0 : tout le réseau
docker run -p 127.0.0.1:8000:8000 mon-image    # publié sur la boucle locale seulement
```

Le format est `IP_HÔTE:PORT_HÔTE:PORT_CONTENEUR`. Sans IP au début, Docker publie sur toutes les interfaces. En plus, Docker écrit ses propres règles `iptables`, ce qui peut contourner un pare-feu comme `ufw`.

Et attention, le SDK Python de Docker inverse l'ordre : le dictionnaire va du port **conteneur** vers l'**hôte**.

```python
client.containers.run("img", ports={"8000/tcp": ("127.0.0.1", 8000)})
#                                    conteneur      (IP hôte, port hôte)
```

Sans l'IP dans le tuple, le SDK publie aussi sur `0.0.0.0`.

### Comment vérifier ce que vous exposez

Sous Linux, `ss -ltn` liste les ports en écoute avec leur adresse :

```
127.0.0.1:8000   -> boucle locale uniquement
0.0.0.0:8000     -> toutes les interfaces (IPv4)
*:8000 ou [::]:8000 -> toutes les interfaces (IPv6 inclus)
```

Faites-le sur vos propres projets : c'est la vérification la plus rapide et elle ne ment pas.

### La règle à retenir

* **Application locale** (outil de bureau, serveur de développement) : `127.0.0.1`, toujours, même en production.
* **Vrai serveur**, joignable par design : `0.0.0.0` peut se justifier, mais avec authentification, TLS et en général un reverse proxy devant.
* **Conteneur** : `0.0.0.0` à l'intérieur, mais publication du port sur `127.0.0.1:` à l'extérieur, sauf si vous voulez réellement exposer le service.
* **Dans tous les cas**, un serveur local doit vérifier `Host` et `Origin`, parce que le navigateur est un pont entre le web et votre machine.

Une ligne de configuration peut décider de qui a le droit de parler à votre application. Elle mérite d'être relue à chaque fois.

## en

> *This article grew out of a security review of Workbench carried out with Claude, an AI assistant from Anthropic. The experiments and tests quoted here were run during that review.*

### Context

Mediakit is a desktop application: you install it, it starts a small FastAPI server on your machine, and the interface opens in your browser. Exactly one person is supposed to talk to it: whoever is sitting in front of the computer.

Yet while rereading the startup code during a security review, one line stopped me:

```python
host="0.0.0.0",
```

It worked perfectly, which is exactly the problem: that line never raised a single error. It simply made Mediakit's API, **with no authentication at all**, reachable from every network the computer was connected to.

### A listening address is not a destination address

When a server starts, it chooses **which network interface** it listens on. That is what the `host` argument does. A machine has several: the loopback (`127.0.0.1`, which never leaves the machine), Wi-Fi, Ethernet, sometimes a VPN or Docker.

* `127.0.0.1`: the server only listens on the loopback. Only this machine can connect.
* `0.0.0.0`: "all interfaces". The server answers on every address the machine has.

I checked it with a few lines of Python. I bind a server, then try to connect through the loopback address and through the machine's network address (`192.0.2.2` here):

```
server bound to 127.0.0.1 -> via 127.0.0.1: connected | via 192.0.2.2: ConnectionRefusedError
server bound to 0.0.0.0   -> via 127.0.0.1: connected | via 192.0.2.2: connected
```

Same program, same port. The only difference is the value of `host`, and it decides whether another device can knock on the door.

One confusing detail: `0.0.0.0` means something else on the **client** side. If you *connect* to `0.0.0.0` on Linux, the connection lands on your own machine. I tested that too. We will come back to it, because it is exactly what caused a browser vulnerability.

### Why 0.0.0.0 is so tempting

Because it "works everywhere". A server on `127.0.0.1` is invisible from a Docker container, from WSL, from your phone. A server on `0.0.0.0` answers everyone, and the problem disappears. Tutorials recommend it by reflex, and many development tools offer it as an option.

The trap is that we fix a **connectivity** problem by opening a **security** hole without noticing, because everything keeps working.

### What it exposes

On the Wi-Fi of a café, a university or a coworking space, any device on the same network could call Mediakit's API. The worst part in my case: Mediakit offers an "advanced mode" that lets the client run commands on tools like FFmpeg with chosen options. An API that launches processes, open to the local network without a password, is an open door.

### Even 127.0.0.1 is not enough

Switching to `127.0.0.1` solves the network problem. But one door remains that many forget: **your browser**.

When you visit any website, that page's JavaScript runs *on your machine* and can send requests to `http://127.0.0.1:PORT`. Three attacks follow:

* **CSRF**: a POST `fetch()` with a `multipart/form-data` body is a "simple request" for the browser, which sends it **without asking permission** (no CORS preflight). The page cannot read the response, but the server has already performed the action.
* **Cross-site WebSocket**: WebSockets are not subject to any CORS check. Any page can connect and read a job's logs.
* **DNS rebinding**: a malicious site points `evil.example` at `127.0.0.1` after the fact. For the browser, your application then becomes "same origin" as the page.

And `0.0.0.0` itself was exploited on this side. In 2024, Oligo Security published the "0.0.0.0 Day" flaw: websites could reach local services through `0.0.0.0`, bypassing the browsers' protections against private-network access. Browsers have since started blocking those requests. But the lesson stands: **a local application must not assume the browser protects it**.

### The defence: check Host and Origin

Two headers are enough to close those doors. A browser always sends `Origin` on cross-origin requests and WebSockets, and `Host` carries the name used to reach the server.

```python
LOOPBACK = {"127.0.0.1", "localhost", "::1"}

def refuse(headers) -> str | None:
    if hostname(headers.get("host", "")) not in LOOPBACK:
        return "Host not allowed"            # anti DNS rebinding
    origin = headers.get("origin")
    if origin and urlsplit(origin).hostname not in LOOPBACK:
        return "Origin not allowed"          # anti CSRF / cross-site WebSocket
```

I turned this into a reusable middleware (`LocalOnlyGuard`) for Workbench. Verified in real conditions, on the running server:

```
POST with  Origin: https://evil.example  ->  403 FORBIDDEN_ORIGIN
GET  with  Host: evil.example:8768       ->  403 FORBIDDEN_ORIGIN
GET  from the app's own interface        ->  200
```

Clients that are not browsers (curl, scripts) send no `Origin` and are still accepted as long as `Host` is local. The application's own interface keeps working normally.

### The Docker trap

Inside a container, an application usually listens on `0.0.0.0`: otherwise Docker could not forward traffic to it. That is not a flaw. What decides exposure is the **published port**:

```bash
docker run -p 8000:8000 my-image              # published on 0.0.0.0: the whole network
docker run -p 127.0.0.1:8000:8000 my-image    # published on the loopback only
```

The format is `HOST_IP:HOST_PORT:CONTAINER_PORT`. Without an IP at the start, Docker publishes on every interface. On top of that, Docker writes its own `iptables` rules, which can bypass a firewall such as `ufw`.

And beware: Docker's Python SDK reverses the order. The dictionary goes from the **container** port to the **host**.

```python
client.containers.run("img", ports={"8000/tcp": ("127.0.0.1", 8000)})
#                                    container      (host IP, host port)
```

Without the IP in the tuple, the SDK also publishes on `0.0.0.0`.

### How to check what you expose

On Linux, `ss -ltn` lists the listening ports with their address:

```
127.0.0.1:8000        -> loopback only
0.0.0.0:8000          -> all interfaces (IPv4)
*:8000 or [::]:8000   -> all interfaces (IPv6 included)
```

Do it on your own projects: it is the fastest check and it does not lie.

### The rule to remember

* **Local application** (desktop tool, development server): `127.0.0.1`, always, even in production.
* **A real server**, reachable by design: `0.0.0.0` can be justified, but with authentication, TLS and usually a reverse proxy in front.
* **Container**: `0.0.0.0` inside, but publish the port on `127.0.0.1:` outside, unless you really want to expose the service.
* **In every case**, a local server must check `Host` and `Origin`, because the browser is a bridge between the web and your machine.

One line of configuration can decide who is allowed to talk to your application. It deserves a second look every time.
